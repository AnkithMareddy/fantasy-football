# Model changelog
Read this before explaining any change in odds between reports. Newest first.

## 2026-10-22 (5) - the site was never actually usable on a phone
- Root cause, and it had been true all season: site/index.html had no viewport meta tag. A phone therefore laid the page out at 980px and scaled it down, so the text came out unreadable AND every responsive @media rule already in the file (640px, 760px, 860px) silently never fired. The three game pages had the tag; the one everyone opens did not.
- Standings table: eight columns in a ~345px panel meant playoff and title odds - the entire point of the page - sat off-screen behind a sideways scroll nobody finds. On phones it now shows team / projected record / playoff / title and hides actual record, points for, bye odds and FAAB. Two things had to be fixed for that to work: the rule had to be scoped to the standings (Team Tendencies shares the same wrapper class but has different columns, and forcing its overflow visible would have pushed the whole page sideways), and the base `table` rule sets min-width:600px, which pinned the table wider than the panel regardless of the width asked for. Long team names now truncate with an ellipsis instead of running into the record column.
- Navigation: every page rolled its own. index.html had three gold header buttons; the other three each had a different row of small inline text links. Nothing told you where you were. New site/nav.js is one shared component used by all four - a bar under the header on desktop, a fixed tab bar at the BOTTOM on phones, where a thumb can actually reach it, with the current page marked. deploy_site.sh ships it.
- Touch targets: an audit at 390px found 21 controls under Apple's 44px minimum on the arcade page alone (week chips 32px, panel tabs 41px). Now 0 across all four pages.
- Two bugs I introduced and caught by measuring rather than eyeballing: a 16px minimum font meant to stop iOS zooming on focused inputs was applied to buttons too, which tripled the size of the week and matchup chips (it belongs on form fields only); and a first attempt at `position: sticky` for the tab bar would not have pinned at all, because bottom-sticky only holds an element that sits last in its container.
- Worth recording to avoid a false alarm later: in a scaled device emulator window.innerWidth and documentElement.clientWidth disagree (456 vs 390 here), which makes a fixed full-width bar look clipped. On a real phone they are equal - verified at a width where they match, where the bar spans exactly and all four tabs render 175x58.
- Also added theme-color and the iOS web-app meta tags so the browser chrome matches the board and the site behaves when saved to a home screen.


## 2026-10-22 (4) - the drill is a run now, not an endless list
- The previous entry made the drill honest; it did not make it a game. It was infinite practice with a counter: no clock, no fail state, no difficulty curve, nothing at stake.
- RUN mode: ten spots, a 20-second play clock on each, three strikes and you are out, then an end screen with a shareable grade grid and a best-run record. Letting the clock expire is graded as the WORST option on the board, not a neutral skip - in a live week an unset lineup is the worst outcome available, so the game should treat it that way.
- Difficulty ramp: drill.py now exports `gap` (win% between the best option and the second best) and a tier. A wide gap means one option is plainly right; a narrow one means you have to know the players. Runs open on easy and finish on hard. Spots below 0.5pp are tagged `coinflip` and excluded from runs - when every option grades green there is no call to make and scoring it would be noise. Current mix across 43 drills: 29 easy, 9 medium, 3 hard, 2 coinflip.
- Scoring: grade points x a combo multiplier, plus a time bonus of 5 points per second left. The time bonus is what makes the clock bite - narrowing it to two and dithering costs real points even when you end up right.
- PRACTICE mode keeps the old endless, clockless behaviour, because that is the better way to actually learn the league.
- Verified by playing it in a browser, including the failure paths: a wrong pick grades BIG MISS and takes a strike, an expired clock auto-grades and takes a strike, three strikes ends the run and writes the record. One bug found and fixed that way - the card still read "0/0 runs cleared" after a run ended, because the record was written but the card was never redrawn.
- Incidental confirmation that the hindsight fix is real: the week-6 Gujju8 RB spot now grades Emanuel Wilson as the best call and notes it was the same call the manager made. Before the fix it graded that call a mistake.


## 2026-10-22 (3) - the arcade games were solvable without thinking, and the drill was quietly using hindsight
- Reported by the user: "if you just pick the highest ppg swap you win every time". Measured it rather than assuming: the highest-projection option was the single best call in 72 of 72 drills, and graded green in 72 of 72. It was not a game, it was a sorted list.
- Worse, the options were emitted sorted best-first and the page read options[0] as the answer, so the winning strategy was "click the first button" - no reading required. comeback.py had the same leak and sorted by new_total, which is the points the swapped-in player ACTUALLY scored, so its first option was the hindsight-best one.
- Checked whether this was fixable by reframing the question, and it is not. Under winprob.py's gamma model a player's distribution is set by (mean, position CV), so for a fixed opponent and rest-of-lineup, win probability rises monotonically with the mean. Scanned 1,849 live known-deficit spots ("you need N points from this slot"): in 0 of them was a lower-projection player the better call. The "down big, take the boom/bust guy" intuition does not hold here - tail weight is mean x CV^2, so a 14-point RB (5.04) and a 9-point TE (5.06) have nearly identical tails, and the CV spread within FLEX (0.60-0.75) is far too narrow to overcome a mean gap at a playable probability.
- So the fix is informational, not mechanical: options are now shuffled (seeded on the spot's identity, so the order is stable for everyone and across runs), and no projection is shown until the call is made. The reveal then gives win%, projection, actual points and the player's form going in. Both games now identify the best option by id (best_pid / best_in_pid); taking options[0] is no longer correct and the generators say so.
- Found while fixing it: drill.py was grading historical calls with season_input.json's ppg, which is a WHOLE-season average built from today's rosters. Grading a week-4 decision with a number containing weeks 5-7 is hindsight, and drill.py's docstring explicitly claimed it had none. It also hid role changes - the week-6 RB drill graded Travis Etienne (season ppg 10.35, but he had missed weeks 4 and 5 injured) as the best call over Emanuel Wilson (season ppg 3.53, because his weeks as a backup are averaged in, though he had just gone 25.5 and 12.2 as the starter). Any manager watching that week starts Wilson, and the drill called that a mistake.
- Drills are now graded on a baseline built only from completed weeks BEFORE the drill's week (gamelog.ppg_through). Consequences, stated plainly: weeks 1-2 no longer produce drills (nothing to project from), players with fewer than two prior appearances or a zero average are no longer options, and the drill count went from 72 to 43. Fewer, but none of them are graded with information the manager could not have had.
- Also per the user's ask for more choices: a slot now needs at least three legal candidates to be drillable (two options is a coin flip), and near-ties in leverage break toward the slot with the wider choice set. Scoring is now points with a streak multiplier rather than a bare grade.
- Verified end to end in a browser, not just in the data: first-option-is-best fell from 100% to 37% (chance is ~33%), 0 lineup diagrams render with "?" holes, 0 zero-projection options remain, and the reveal shows win%, projection, actuals and form.


## 2026-10-22 (2) - the two refresh paths could have raced; one shared lock now
- Introducing the launchd job created a problem that didn't exist before: it fires at 8:05 and 23:05, the Claude routine fires a few minutes later after its dispatch jitter, and the routine's prompt tells it to run ./update.sh directly. Two runs part-way through writing the same state/*.json files would have left a torn mix of both.
- New lock.sh, sourced by update.sh and deploy_site.sh as well as autorefresh.sh. A directory lock (mkdir is atomic; macOS has no flock). Contenders WAIT rather than skip, because a routine that has just written new injury overrides needs a run that reflects them - stale numbers are worse than being a few minutes late.
- A nested call can't deadlock on a lock its own parent holds: autorefresh.sh takes it once and exports PIPELINE_LOCK_HELD so update.sh and deploy_site.sh skip acquiring. The owner flag is deliberately NOT exported, so a child exiting cannot release a lock its parent still needs.
- A lock orphaned by a crash or reboot is reclaimed after 60 minutes, so a dead run can't wedge the pipeline until someone deletes it by hand.
- deploy_site.sh needed care: it already had an EXIT trap for its temp dir, and EXIT traps replace rather than stack, so the lock release had to be added to the existing trap instead of as a second one.
- Tested rather than assumed, four cases: nested call doesn't deadlock and a child exit doesn't release the parent's lock; an independent second caller waits (30s against a 25s holder) instead of proceeding immediately; a 90-minute-old lock is reclaimed at once; a fresh lock is NOT reclaimed. Then a full autorefresh.sh run, clean, lock released.

## 2026-10-22 - the daily routine froze for four days; site refresh no longer depends on it
- Symptom the user reported: no texts, no site updates, routines not running. Site had been stale since 2026-10-18 and the live data.json still said week 6 on 2026-10-22.
- Cause, exactly: the scheduled Claude routine runs in `default` permission mode, so every Bash command needs a human to click Approve. The Sunday 2026-10-18 11:06 PM run started, read README.md (auto-allowed), then issued its first Bash call at 06:06:40Z and stopped there waiting for approval. Nobody was awake. The run stayed in `running` state for four days, and because the scheduler will not start a run while one is in flight, the next SEVEN scheduled runs (Oct 19 8AM through Oct 22 8AM) never fired at all. One unanswered prompt took the whole pipeline down silently.
- Not a model defect, and not a data problem: every script was fine. The orchestration was the single point of failure.
- Fix: new autorefresh.sh runs update.sh then deploy_site.sh with no Claude session involved, so the model run and the site publish can never block on a permission prompt. Sets its own PATH (launchd starts near-empty), takes an mkdir lock so runs cannot stack, logs to state/autorefresh.log, and on failure leaves the previously published site in place rather than pushing a half-built one.
- Verified, not assumed: ran it under `env -i` with only HOME/USER/TMPDIR set, which is roughly what launchd gives a job. Full pipeline completed and the git push to GitHub Pages succeeded headlessly from the keychain. Live site now serves week 7.
- What autorefresh.sh deliberately does NOT do: injury research, writing the report, and texting. Those need judgment and, for texting, the user's consent, so they stay with the Claude routine. If the script is the only thing that ever runs, the numbers stay current and no text goes out.
- Still needs a human once: installing the launchd agent and setting the routine's permission mode are both outside what this session is allowed to do.

## 2026-10-18 (2) - drill.py and comeback.py were not reproducible (fixed)
- Found while refactoring: two identical runs of drill.py produced different answers - 16 of 60 drills disagreed on which slot was the key decision or what the call cost. Cause was pool(), which iterates a set() of player ids. Python randomises string hashing per process, so the set's order changed run to run, which changed the order random draws were consumed in, which changed every downstream number. comeback.py shared the code and the bug.
- Fixed by sorting the id set before iterating. Verified: two consecutive runs of each now differ in 0 rows.
- Worth being plain about what this means - every drill and comeback published before this fix was one sample of a wobbling process, not a stable answer. The grades were still computed correctly within a run; they just weren't repeatable. They are now.
- Not a change to the season model: runseason.py, season.py and the playoff odds were never affected, since neither reads from a set.

## 2026-10-18 - Questionable/Doubtful are now probabilities, not verdicts (runseason.py)
- Found a real gap: a player tagged QUESTIONABLE was modelled as fully healthy. The tag was never read at all - only IR/PUP/SUS/NA/COV (out 4 weeks) and OUT/DOUBTFUL (out 1 week, deterministic) were. That silently treated 17 currently-tagged players league-wide as 100% available.
- Game-status tags now resolve as a fresh coin flip each simulated season: DOUBTFUL misses 93% of the time, QUESTIONABLE 30%. Rates come from final-injury-report studies - Footballguys' "Chance to Play" work puts Questionable at 70.7% playing and Doubtful at 6.9%; ESPN found roughly 75% for Questionable after the 2016 definition change. OUT and IR are unchanged and still deterministic.
- Measured, not assumed: re-ran 4,000 sims before and after against the same seed. Direction is right - Ulyssesbo (3 tagged players) -1.8pp playoff odds, Gujju8 (1) -0.9pp, arabdhab (0 tagged) +1.7pp. Per-team SE at 4k sims is ~0.8pp, so no single team's move clears noise on its own; the evidence is the pattern across teams, and the production run uses 10,000 sims.
- NOT changed, and worth recording because an earlier read of mine was wrong: position-level injury risk already existed (season.py DEF_AVAIL feeds a per-position availability into the hazard), and injury LENGTH already came from a severity distribution (runseason.py dur(): 42% one week, 26% two, down to 4% season-ending). Neither needed fixing.
- Still missing, deliberately: a Questionable player who does suit up often underperforms. No sourced magnitude for that, so no coefficient was invented.

## 2026-09-29 (2) - Regression Case: an adversarial-to-us sensitivity scenario
- runseason.py gained three more levers (MY_TEAM, MY_CV_MULT, MY_MISTAKE_RATE, RIVAL_LUCK_MULT), all no-ops until MY_TEAM is set (verified baseline still byte-identical). MY_CV_MULT adds extra bust variance to one team only; MY_MISTAKE_RATE gives that team a real weekly chance of starting a worse player than it should (the single best bench option at a random position is deliberately benched, not just variance); RIVAL_LUCK_MULT runs every other team hot.
- sensitivity.py's 4th scenario, "Regression Case," points all three at our own team (bust x1.5, 20%/week mistake chance, opponents scoring x1.08) - directly answers "is the model just assuming we deserve 1st." It isn't: this scenario alone drops us from 73.0% to 45.4% playoff odds and from 1st to 8th of 12 - real downside the baseline doesn't show by itself, because a favorite naturally look strong in a model that assumes everyone plays their projection.
- Read-only, same as the other two scenarios - never overwrites season_out.json or feeds back into the baseline, start/sit, or any other number.

## 2026-09-29 - what-if roster scenarios (runseason.py)
- runseason.py now also accepts a SEASON_INPUT env var (defaults to season_input.json, so the normal pipeline run is unaffected - verified byte-identical output with no override). Lets a one-off question like "what does the rest of the season look like if I add X and drop Y" actually run the real 10,000-sim model against a modified roster copy instead of a guess, without ever touching the baseline season_out.json.
- Used this for a real question: swapping AJ Dillon -> Ollie Gordon II and Travis Kelce -> Kalif Raymond (both free agents in this league, both surfaced as waiver targets after De'Von Achane's Week 3 ACL tear). Baseline vs what-if: playoff 73.0% -> 86.3%, bye 31.7% -> 49.9%, title 14.9% -> 24.9%. Scratch input/output files are gitignored (state/whatif_*.json) - this is a one-off analysis tool, not a standing feature.

## 2026-09-12 - added start/sit analysis
- New startsit.py, run by update.sh, writes state/latest_startsit.txt.
- Compares the live current lineup (Sleeper's starters right now) against a conservative-floor-optimal lineup for the user's own team only. Floor = season.py's ppg discounted by half of runseason.py's weekly CV per position (e.g. a WR's floor is ppg*0.675, an RB's is ppg*0.70) — a deliberate buffer against boom/bust, not a median or ceiling number.
- Players out this week (bye, an injury_overrides return_week beyond the current week, or a Sleeper OUT/DOUBTFUL/IR/PUP/SUS/NA status) are floored to 0 and labeled unavailable rather than penalized as a bad start.
- A player whose NFL game has already been played uses the real score (from Sleeper's starters_points for starters, players_points for bench — refresh.py now captures both), never a projection, and is never flagged as swappable.
- Doesn't touch odds/projections for other teams or the season sim — this is lineup advice only, no effect on playoff/title numbers.
